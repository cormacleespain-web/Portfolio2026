## 2026-07-11 — Site-wide premium polish — Stage 4 (Phase D)
**Ran:** Motion choreography pass. Extended the site's existing premium cubic-bezier (`[0.16, 1, 0.3, 1]`, already used in `Hero.tsx`) to every entrance animation still on Motion's built-in `"easeOut"`: the shared `ScrollReveal.tsx` (used by most sections — single fix, broad reach, same leverage pattern as the `Section.tsx` fix in Phase A), plus `CaseStudyHero.tsx`, `CaseStudyTimeline.tsx`, `CaseStudySection.tsx`, `CaseStudyImpact.tsx`. Durations bumped modestly (0.4-0.5s → 0.5-0.7s) to read as "heavy fade-up" per high-end-visual-design's guidance, not sluggish. Left hover/click micro-feedback (nav, cards, chat widget, `<0.3s`) on their existing quick easing — slowing those down would hurt the snappy feel that's part of the same premium reference (Apple/Revolut), so this was a deliberate exclusion, not an oversight.
Checked for the banned `window.addEventListener('scroll')` animation-driver pattern: found one scoped `element.addEventListener('scroll')` in `AllWork.tsx`'s carousel (tracks which card is centered for a live region, `passive: true`, already not per-pixel-driving a transform). Judged as a legitimate scroll-position read, not the banned pattern (which specifically targets page-level parallax/animation drivers) — left as is.
**Found and fixed a real accessibility gap, not in the original audit:** none of the Motion-library animations anywhere in the app (`ScrollReveal`, all case-study entrances, card hovers, footer wave, etc.) respected `prefers-reduced-motion` — only the hand-written CSS animations did. Added `components/ui/MotionConfigProvider.tsx` (`<MotionConfig reducedMotion="user">`) wrapping the app body in `layout.tsx`, which makes every Motion animation site-wide honor the OS setting automatically, per design-taste-frontend's mandatory Section 6.B rule.
